#### Task 2.3 — Spheres as entities, driven from Rust
<!-- id: task-1794268800000-2 -->
The spheres of Task 2.2 become entities of the `World`: a `Sphere` component described in a `.ron` schema (center, radius, color, material), edited in the inspector for free (descriptors). `RayTracePass` takes the `World&` and packs every `Sphere` into the storage buffer each frame; the engine still knows nothing about spheres (the pass is the game's). Rust gets `Query::iter` (iterating every entity with a `T`: a new `HostAPI` function, `GameAPIVersion` 4) so a system can move them; C++ gets typed access (`static constexpr ComponentID ID` in the generated structs). Both moved here from Task 1.4. Open question: who creates the entities. C++ does for now (`main.cpp`); scripts creating them need `HostAPI::CreateEntity`/`AddComponent`, and since the `World` outlives reloads, a spawning system run on every `on_load` would duplicate them. That, and saving the scene, can wait (world serialization is Wave 3+).

#### Task 2.x — BVH, more shapes, triangle meshes in the ray tracer
<!-- id: task-1794268800000-3 -->
After Task 2.3 (*Ray Tracing: The Next Week* territory). Other analytic shapes (quads, boxes: an intersection function each, like the sphere). A bounding volume hierarchy built on the CPU, flattened into a storage buffer and walked in the shader without recursion: needed once there are many objects. #### Task 2.2 — Ray Tracing in One Weekend, in a compute shader
<!-- id: task-1794268800000-1 -->
*Ray Tracing in One Weekend* ported to `RayTracer.hlsl`, every piece of data owned by C++ (`RayTracePass`). Camera as a per-frame uniform (set 0, binding 0; the storage image moves to binding 1), spheres as a `StorageBuffer<Sphere>` (set 1), C++ structs matching the HLSL layout (`static_assert` on their sizes). Then the book's chapters: ray–sphere intersection, normals, several samples per pixel, diffuse/metal/dielectric materials, a defocus camera. What the book doesn't have, being CPU code: a random number generator in the shader (PCG, seeded from pixel + frame), and recursion turned into a loop with a bounce limit (HLSL has none). Stretch: progressive accumulation while the camera doesn't move (the `R16G16B16A16Sfloat` target suits it). The user writes it; Claude reviews. Done 2026-11-12 (user): chapters 2–10 (camera with yaw/pitch/FOV instead of ch. 12, jittered samples, diffuse with a bounce loop and an analytic unit vector, gamma left to the sRGB swapchain, materials in their own storage buffer indexed by the sphere: Lambertian, Metal with fuzz), progressive accumulation as a post-process pass (reset on any edit or resize) and 2× SSAA. Done 2026-11-12 (user): ch. 11 — dielectrics (Snell, total internal reflection, Schlick), hollow spheres as one shape (an inner radius whose surface has its normal toward the center, instead of the book's second sphere with an inverted index), glass tinted by the distance travelled inside it (Beer–Lambert: `Albedo^(distance / AbsorptionDistance)`) instead of per surface, the bounce limit in the camera uniform. Done 2026-11-13 (user, Claude fixing the units): ch. 13 — defocus blur through a thin lens (rays from a uniform point on the lens disk toward the pinhole ray's point on the focus plane), driven like a real camera: the focal length a full-frame sensor needs for the FOV, an f-stop (lens radius = f / 2N), a focus distance in metres, plus an artistic bokeh scale. Done 2026-11-13 (user, Claude scaffolding the pass): depth of field as a post-process to compare with the lens — a depth output (first hit of a pinhole ray through the pixel's center, along the camera's axis), `PostProcessPass` taking several inputs, `DepthOfField.hlsl` (circle of confusion from the same lens settings, a golden-angle gather weighted by whether each neighbour's CoC reaches the pixel), toggled from the RayTracer panel. The story for the devlog: `docs/wave-2-ray-tracer-story.md`. Done 2026-11-13: the book's final scene (ch. 14's cover, generated on the CPU with a seeded `std::mt19937`: a ground, 482 random small spheres, three big ones; buffers raised to 512), one sample per frame left to the accumulation, and the frame rate in the editor's menu bar. Baseline for the BVH: 486 spheres, ~8 FPS on the M4 Pro (1 sample, 10 bounces, 2× the viewport's resolution), every ray testing every sphere. Closed 2026-11-13.

#### Task 0.4 — `gram build --ci`
<!-- id: task-1789300000000-4 -->
`gram build --ci` iterates every entry in a module's `targets` (currently `linux`/`windows`, via `x86_64-w64-mingw32-g++`/`rustc --target x86_64-pc-windows-gnu`) and places each binary in `../builds/<project>_<version>_<target>/<binary>` (sibling to the project dir). A plain `gram build` (no `--ci`) only ever builds for the host it's run on, ignoring the rest of `targets`. Simplified from the original `<date>-<commit>` layout — dropped since there's no actual CI pipeline consuming these artifacts yet (see CLAUDE.md's "No CI/CD until..." non-goal); revisit if/when one exists.
