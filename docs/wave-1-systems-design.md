# Wave 1 — Systems: a generic GameAPI

Status 2026-11-02: **adopted, steps 1–2 done** (registry + dispatcher, events; see *Steps*). Proposed 2026-11-01. Builds on `wave-1-rust-gameplay-design.md` (state in C++, a stateless Rust `cdylib`, `ObjectId`/`Handle`). Statements about Bevy come from memory; re-check them before depending on the details.

## The problem

Today `GameAPI` lists the game's functions one by one:

```rust
pub struct GameAPI { version, on_load, on_unload, greet }
```

Every new piece of gameplay (`spin`, `on_hit`, …) means a new field in Rust, the same field in C++, a new `GameAPIVersion`, a C++ rebuild and a restart. The engine has to know every function of the game by name. That's backwards: the engine should run *whatever the game has*, without knowing it in advance.

The goal: **`GameAPI` is the same for every game and never grows.** The game's functions become *data* the engine receives, not fields in a table.

## Vocabulary

- **System**: one function of gameplay logic. It holds no state; it reads and changes components owned by the host. `greet` and `spin` are systems.
- **Stage**: *when* a system runs. `Update` (every frame), `Event("greet")` (when that event is emitted), later `Load`, `FixedUpdate`, …
- **Schedule**: the ordered list of systems for each stage. Running a frame = walking the `Update` list.
- **Registry**: where the systems are recorded (name, stage, how to call it). Whoever owns the registry decides what runs.
- **Event**: a named message (`"greet"`) emitted by someone (a UI button, another system, a collision) and handled by the systems subscribed to it. The emitter doesn't know who handles it.
- **Context**: what a system gets when called: `dt`, the current event, and access to components.

## How Bevy does it

```rust
fn spin(time: Res<Time>, mut query: Query<&mut Transform, With<Spinner>>) { ... }

App::new().add_systems(Update, spin).run();
```

Two separate ideas, worth keeping apart:

**1. Registration + schedule.** `add_systems(Update, spin)` stores `spin` in the `Update` schedule. The engine knows nothing about `spin` at compile time; each frame it walks the list. That is the whole "the engine runs my functions by itself" part, and it's simple.

**2. Parameters deduced from types.** This is the clever part. Each parameter type (`Res<Time>`, `Query<…>`) implements a trait, roughly:

```rust
trait SystemParam {
    fn fetch(world: &World) -> Self;   // how to build this parameter from the world
}
```

and Bevy implements "can be a system" for every function whose parameters are all `SystemParam`s, with one `impl` per arity, generated by a macro:

```rust
impl<F, A: SystemParam> IntoSystem for F where F: Fn(A) { ... }        // 1 parameter
impl<F, A: SystemParam, B: SystemParam> IntoSystem for F where F: Fn(A, B) { ... } // 2 parameters
// ... up to 16
```

The result is a `Box<dyn System>`: one abstract shape for functions of any signature (*type erasure*). The schedule only holds `Box<dyn System>`s and calls `run(world)` on each. The parameter types also tell Bevy which data each system reads and writes, which is how it runs non-conflicting systems in parallel.

For Gram, idea 1 is what makes `GameAPI` generic. Idea 2 is ergonomics, and can come later on top, without changing the contract with C++ (see *Later: parameters from types*).

## Gram's version

### Who owns what

**C++ owns the registry and the schedule; Rust only describes its systems.** Same rule as everything else (C++ owns all state), and it buys editor-style visibility: the inspector can list the systems, their stage and how long each took, and switch one off. The list isn't game state in Rust's sense either: it's code, rebuilt on every load, like the host table.

### The contract

`GameAPI` shrinks to a fixed shape, and gets **one** function that runs any system, by index:

```rust
#[repr(C)]
pub struct GameAPI {
    pub version: u32,
    pub on_load: extern "C" fn(host: *const HostAPI) -> *const GameAPI,
    pub on_unload: extern "C" fn(),
    pub run_system: extern "C" fn(index: u32, ctx: *mut SystemContext),
}
```

During `on_load`, Rust tells C++ about each system through a new `HostAPI` function:

```rust
#[repr(C)]
pub struct SystemDesc {
    pub name: [u8; 64],      // "greet": for the inspector and the log
    pub stage: Stage,        // #[repr(u32)]: Update, Event, ...
    pub event: [u8; 64],     // the event name when stage == Event, empty otherwise
    pub index: u32,          // what C++ passes back to run_system
}

pub struct HostAPI {
    pub log: ...,
    pub register_system: extern "C" fn(desc: *const SystemDesc),
}
```

Why one `run_system(index)` instead of one function pointer per system: a Rust `fn(&mut Context)` isn't `extern "C"`, so C++ can't call it directly; each would need its own `extern "C"` wrapper with `guard`. With a dispatcher there is exactly one wrapper, written once, and the systems stay plain Rust functions in a list:

```rust
// game-logic: the whole list of systems. Code, not state: a const array.
const SYSTEMS: &[(Stage, &str, &str, fn(&mut Context))] = &[
    (Stage::Update, "spin", "", spin),
    (Stage::Event, "greet", "greet", greet),
];

extern "C" fn run_system(index: u32, ctx: *mut SystemContext) {
    guard(AssertUnwindSafe(|| {
        let Some((_, _, _, system)) = SYSTEMS.get(index as usize) else { return };
        let Some(ctx) = (unsafe { ctx.as_mut() }) else { return };
        system(&mut Context::new(ctx));
    }));
}
```

`on_load` walks `SYSTEMS` and calls `register_system` for each. A new system is one line in `SYSTEMS`: no C++ change, no version bump, picked up by a reload.

### Lifecycle, with reload

```
C++ (GameAPILoader)                               Rust (game-logic)
───────────────────                               ─────────────────
load copy
OnLoad(&host)                          ──►        init; for each entry of SYSTEMS:
registry += {greet, Event "greet", 1}  ◄──          host.register_system(desc)
registry += {spin, Update, 0}          ◄──
return &GAME
every frame:
  for each Update system: RunSystem(i, ctx{dt})       ──►  spin(ctx)
  for each queued event e:
    for each system of Event(e): RunSystem(i, ctx{e})  ──►  greet(ctx)
on a new build:
  OnUnload()                           ──►
  clear the registry  ← before unloading: its indices belong to the old library
  unload; load the new copy; OnLoad    ──►        registers again (maybe a different list)
```

The one rule: **the registry is cleared before the library goes away**, for the same reason `m_Game = nullptr` comes before `reset()` today. Indices from the old library mean nothing to the new one.

### Events: the Greet button

The Inspector stops calling Rust. It emits an event:

```cpp
if (ImGui::Button("Greet")) m_Events.Emit("greet", entity);
```

C++ queues it and, after the UI has run, dispatches each queued event to the systems registered for it. The button no longer knows `greet` exists; with no system subscribed, nothing happens (and the inspector can show that). Queueing instead of calling immediately keeps one rule simple: Rust only ever runs from the dispatcher, never from the middle of UI code.

Event payload, first version: the target `ObjectId` and nothing else. Typed payloads (a hit's position, a damage value) can later be described in a `.ron` schema exactly like components.

### Context: what a system can touch

```rust
#[repr(C)]
pub struct SystemContext {        // filled by C++ for each call
    pub dt: f32,
    pub event_target: ObjectId,   // invalid when not called for an event
}
```

`gram_core::Context` wraps it and holds all the `unsafe`:

```rust
fn greet(ctx: &mut Context) {
    let Some(target) = ctx.event_target() else { return };
    ctx.with_mut::<Greeting>(target, |greeting| {
        greeting.text.set("Hello world from Rust");
    });
    info!("Greetings from Rust!");
}
```

`with_mut::<Greeting>(id, …)` asks the host for the component (`host.get_component(id, Greeting::ID)` → pointer or null) and lends it to the closure only. That needs two things that don't exist yet, both already planned in Task 1.4:

- **`ObjectId`** (index + generation) and the C++ ID table.
- **A component ID** for each component type, so Rust can say "the `Greeting` of entity X". It comes from the schema: the generator writes `Greeting::ID` on the Rust side and the same number in the C++ descriptor.

Lending inside a closure (instead of returning `&mut Greeting`) is the aliasing protection from the main design doc: the reference can't escape, and a second `with_mut` on the same component can be caught.

Later, iterating: `ctx.each_mut::<Greeting>(|id, greeting| …)`, with the host returning `(pointer, count)` of its component array (layout option 1 in the main design doc).

## What the gameplay programmer writes

Step by step it ends at:

```rust
use gram_core::prelude::*;

fn greet(ctx: &mut Context) { ... }
fn spin(ctx: &mut Context) { ... }

gram_core::export_game! {
    Update => [spin],
    Event("greet") => [greet],
}
```

`export_game!` (a `macro_rules!` in `gram-core`) generates what `game-logic` writes by hand at first: the `SYSTEMS` array, `on_load` / `on_unload` / `run_system` with their `guard`s, `GAME` and `game_get_api`. No `unsafe`, `extern "C"` or raw pointer is left in game code.

## Later: parameters from types

Bevy's idea 2, on top of the same contract:

```rust
fn greet(event: EventTarget, mut greetings: Query<&mut Greeting>) { ... }
```

`EventTarget` and `Query<&mut Greeting>` implement a `SystemParam`-like trait that builds them from the `Context`; an `IntoSystem` trait implemented for `Fn(A)`, `Fn(A, B)`, … (one `impl` per arity, from a macro) turns such a function into a `fn(&mut Context)`. C++ sees no difference. It's the most interesting Rust in this design (traits, generic `impl`s over function types, type erasure), and none of it is needed for the proof of concept.

What it adds besides comfort: the parameters declare what each system reads and writes, which is what a scheduler needs to order systems or run them in parallel. Two `Query<&mut Greeting>` in one system are the aliasing problem again, checked at runtime the way Bevy does when it builds the system.

## Inspector

A "Systems" panel reads the registry: name, stage, event, enabled checkbox, time of the last run. Disabling a system is a flag in C++; it survives a reload if the registry keeps it by name. This panel is cheap and shows the reload working: change `SYSTEMS`, rebuild, the list updates live.

## Steps

1. **Registry + dispatcher, by hand.** `register_system` in `HostAPI`; `run_system` in `GameAPI` (drop `greet`, bump `GameAPIVersion` one last time); the registry in `GameAPILoader`, cleared on reload. One `Update` system that logs once per second. Done when adding a second system to `SYSTEMS` shows up after a reload, with no C++ change.
   Done 2026-11-02, with a few differences from the sketch above: the contract types live in `gram-core::system` (`Stage`, `Descriptor`, `Context`, `Entry` instead of tuples) and `gram-core::game_api` (`GameAPI`, `GAME_API_VERSION`), the systems take `&Context` (C++ owns the time), and `HostAPI` starts with an opaque `Host` pointer (the loader's `this`) that Rust hands back to `RegisterSystem`, the usual C-callback context. `tick` logs once per second without any state: it compares `floor(Time)` with `floor(Time - DeltaTime)`.
2. **Events.** An event queue in C++, dispatched after the UI. The Greet button emits `"greet"`; `greet` becomes an event system. Still a raw pointer to `Greeting` in the context at this step if `ObjectId` isn't there yet.
   Done 2026-11-02: `GameAPILoader::Emit(name)` queues, `OnDrawFrame` takes the queue (`std::exchange`, so an event emitted while dispatching lands next frame) and runs every system registered for each event, then drops it, whether anyone listened or not. Two systems on `"greet"` both run once per click. `greet` doesn't touch `Greeting` yet: it has no way to reach it until step 3.
3. **`ObjectId` + component IDs + `Context::with_mut`**, together with the schema generator (Task 1.4 steps 3 and 3b). The raw pointer disappears.
4. **`export_game!`**, once the hand-written version has settled.
5. **Systems panel** in the inspector.
6. Later: parameters from types, ordering constraints.

## Open questions

- **Order inside a stage**: registration order for now. Bevy has explicit `.before()` / `.after()`; Unity has script execution order. Needed once two systems depend on each other.
- **`Load` vs `Startup`**: a system that runs after every load (rebuilding caches) and one that runs once per world (spawning the first entities) are different things. Which does Wave 1 need? Probably neither yet.
- **Events emitted by Rust**: a system emitting an event (`host.emit`) goes into the same queue, dispatched the same frame or the next? Next frame is simpler and avoids loops.
- **Where the registry and the event queue live**: in `GameAPILoader`, or in a separate `World` layer (Task 1.z mentions one) that the loader fills. The `World` is closer to "C++ owns all state".
