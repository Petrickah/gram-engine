# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It is self-contained: this repo is meant to be cloned standalone on dev machines (Windows, macOS) that don't have the author's Obsidian vault or the `Projects` monorepo it's normally a submodule of — don't assume either is available. Current task-level progress lives in `.gram.kanban.md`; check it first.

## What this is

Gram — a personal game engine (Rust + C++), started from rediscovered passion, not a portfolio obligation. No deadline. Structured in "waves": each wave produces one working artifact plus a devlog post (`petretiberiu.dev`).

## Waves

- **Wave 0 — Gram Build** (done): a pure-Rust CLI build tool — no C++, no runtime deps. Full command set: `gram init`/`build`/`add`/`remove`/`run`, driving a `Gram.ron` project file (serde + `ron-rs`, a format reused later for asset definitions). A `cargo` module kind delegates straight to real `cargo`; a `cmake` module kind scaffolds a C++ project with FetchContent/vcpkg dependency resolution, for when Wave 1 needs it. The project is self-hosting (`gram` builds itself via its own `Gram.ron`). Details: `docs/wave-0-*.md`.
- **Wave 1 — Hello Triangle**: window + Vulkan + triangle + ImGui, C++/Rust interop. C++ owns `main()`, the renderer and **all state** (entities, components, IDs; never reloaded). Rust gameplay logic is a single `cdylib` (gram module `GameLogic`, crate `game-logic` in `Game/Content/`, built as `libGameLogic.dylib`) with no game state of its own, loaded/reloaded via `LoadLibrary`/`dlopen` (copy-on-load) and called through plain `extern "C"`: two `#[repr(C)]` function tables, `HostAPI` (filled by C++, what the engine offers) and `GameAPI` (filled by Rust, what the game offers), exchanged through the one exported symbol `game_get_api`. Shared data is `#[repr(C)]` in host memory, reached from Rust through IDs (`Handle`/`Reference`). `gram/gram-core` is an `rlib` holding the engine-side Rust types (`HostAPI`, `LogLevel`) and the library's side of the contract: `init` (stores a copy of the host table, installs the panic hook), `guard` (`catch_unwind`), `log` and the `info!`/`trace!`/`warn!`/`error!` macros, the `GameAPI` table (`game`), the system types (`system`: `Stage`, `Descriptor`, `Context` with `with`/`with_mut`, `Entry`, `register`), `types::Str<N>` (a `#[repr(transparent)]` fixed `\0`-terminated text buffer: `new`/`set`/`as_str`), `world::ObjectID`, `component` (`ComponentID`, `component_id`, `trait Component`) and `export_game!` (a `macro_rules!` taking `events: { "name" => [systems] }` and `update: [systems]`, generating the system list, `on_load`/`on_unload`/`run_system`, the `GameAPI` table and `game_get_api` inside a `mod __gram_export`); no exported functions, no game state (the stored host table is copied into each loaded library, being an `rlib`). No `bevy_ecs`, no `cxx`/Corrosion (adopted 2026-10-28). Components are described in `.ron` schemas from which `gram build` generates the Rust struct, the C++ struct and a descriptor table (like Anvil's `.mold`); a schema change needs a rebuild + restart, a Rust logic change only a reload. Proof of concept: a `Greeting` component with one text field, edited in an ImGui inspector, surviving a reload — no sphere in Wave 1. Details: `docs/wave-1-rust-gameplay-design.md`.
- **Wave 2 — Ray Tracer**: Vulkan compute shader pipeline; spheres first owned by C++, then driven by Rust entities (position/color/radius).
- **Wave 3+**: raster pipeline, post-processing, asset manager, world serialization — noted, unplanned.

## Methodology — who writes what

- **User writes**: anything that's a new skill being learned for the first time (a CLI with subcommands the first time, Vulkan code following the official tutorial, ECS entity/component/system definitions) — the parts with real learning value.
- **Claude Code writes**: scaffolding (CLI boilerplate, build system wiring, Rust↔C++ interop glue, CMake setup) — plumbing without learning value, once a pattern is already familiar.
- Rule of thumb: first time doing something new → user writes it. Something done many times before (Cargo.toml config, adding a dependency) → delegate to Claude Code.

## Commands

The `gram` crates live in a cargo workspace at `gram/Cargo.toml` (`gram-cli`, package `gram`, plus the `gram-common` library), not the repo root, so plain `cargo` needs `--manifest-path` (or `cd gram` first):

- Build: `cargo build --manifest-path gram/Cargo.toml`
- Run: `cargo run --manifest-path gram/Cargo.toml -- <args>` (e.g. `-- --help`, `-- init hello-world`)
- Test: `cargo test --manifest-path gram/Cargo.toml` — command-level tests in `gram/gram-cli/tests/` (one file per subcommand plus `nested.rs`; read `tests/support/mod.rs` first). They run the real binary in a temp sandbox, kept on failure. The `build`/`run` tests need cmake and a C++ compiler; one test needs crates.io and is `#[ignore]`d.
- Self-hosted (once bootstrapped): from the repo root, `gram/target/debug/gram build` (or `build --ci`, `build --module GameLogic`, `run`) builds the whole tree from the checked-in root `Gram.ron` — `gram` itself, `GramEngine` and the game. The tool's own artifact lands as `build/<project>/<target>/gram`.

## Architecture (current)

The repo is a Gram project tree. Root `Gram.ron` (`gram-engine`, `main: "Runtime"`) holds three modules: `gram` (a nested project → `gram/Gram.ron`: `gram-cli` runtime + `gram-common` library), `GramEngine` (cmake, `STATIC` library) and `Game` (a nested project → `Game/Gram.ron`: `Runtime` → `Game/Runtime/`, cmake runtime, `Module(name: "GramEngine")`; `GameLogic` → `Game/Content/Cargo.toml`, cargo `dynamic`, `Module(name: "gram-core")`). The game is laid out like a Unity project: `Runtime/` is the thin C++ entry point, `Content/` holds what the game is made of (the crate root `lib.rs` at its top, `[lib] path = "lib.rs"`, so scripts can sit in folders next to their data; the shaders in `Content/shaders/`; later schemas and scenes), each kind of file built by its own tool for now. `gram/Gram.ron` also holds `gram-core` (cargo library), the Rust half of the engine's scripting contract.

### Gram Build (`gram/`)

Rust, edition 2024, `clap` (derive) + `serde`/`ron-rs`. `gram-cli/src/main.rs` only parses and prints outcomes; everything else is in `gram-common/src/`:

- `commands/` — clap structs (`Cli`, `InitCommand`, `BuildCommand`, `AddCommand`, `RemoveCommand`, `RunCommand`, `GenerateCommand`) plus thin functions calling `BuildConfig` (see `README.md` for the flag reference).
- `config/mod.rs` — `BuildConfig`, the `Gram.ron` project: `open`/`write` (nested `Gram.ron` files are loaded into one flat module list and split back on write), module add/remove, `build`/`run` over modules, `resolve`/`module_refs` (→ `ResolvedModule`), `artifact_name`, and `add_dependency` returning an `AddOutcome` (`ModuleCreated`/`TargetsAdded`/`DependencyAdded`/`AlreadyPresent`/`NothingToDo`). The CLI decides what to print; the core only reports.
- `config/module.rs` — `ModuleConfig` (`name`, `lang`: `"cargo"`|`"cmake"`|`"gram"`, `kind`: `"runtime"`|`"library"`|`"dynamic"` (cargo only: a `cdylib`), `src`, `deps: Vec<DependencySpec>`, `targets`: `"linux"`|`"windows"`|`"macos"`, plus a `#[serde(skip)]` field remembering its project file), the language-independent build steps and `dir()` (the parent of `src`).
- `lang/mod.rs` — the `ModuleBackend` trait (`manifest_file`, `scaffold`, `compile`, `artifact_naming`, `add_dependency`, `rm_dependency`, `add_module_ref`, `rust_analyzer_manifest`), `backend_for(lang)` — the only place that matches on the `lang` string —, `DependencySpec` (`Registry{name}`/`Git{name,url,tag}`/`Vcpkg{name}`/`Module{name}`, serialized as-is into `Gram.ron`) and `ResolvedModule` (computed at runtime, never serialized: `dir` relative to the project root, `rel_dir` relative to the consumer).
- `lang/cargo.rs`, `lang/cmake.rs`, `lang/gram.rs` — the three zero-sized backends. `lang/vcpkg.rs` — helpers used by cmake (manifest read/write, merging referenced modules' manifests); vcpkg is a dependency source, not a module language.
- `schema/` — component schemas: `find` (the `.ron` files starting with `Component(` under a module, skipping `target/`/`build*/`), `write_if_changed`, and `generate(&[SchemaFile]) -> Generated { rust, cpp }` — the generator proper (written by the user): the serde model (`Component`, `Field`, `FieldType`: `Str(N)`/`F32`/`I32`/`U32`/`Bool`), `Component::layout` (C's offset/size rules, = `#[repr(C)]`) and the two emitters; C++ field names are the schema's snake_case in PascalCase. `BuildConfig::generate(module)` runs it per cargo module and writes `components.generated.rs` / `Components.generated.hpp` next to the `Cargo.toml`, only when their content changed; `gram build` runs it for the whole tree before compiling anything (a cmake module may include a cargo module's header). The generated files are git-ignored (`*.generated.*`).
- `target.rs` — `SUPPORTED_TARGETS`, `validate_targets`, `buildable_on_host`, `cargo_cross_triple`. `directory.rs` — `Directory` file I/O. `vscode.rs` — `write_vscode_settings` (merges into an existing `settings.json`).

gram's cwd is always the project root: `cargo add --path` takes a root-relative path (`ResolvedModule::dir`), cmake's `add_subdirectory` a consumer-relative one (`rel_dir`).

Module language behavior:
- `cargo` modules delegate straight to real `cargo` (`init`/`add`/`rm`/`build`), including cross-compiling to `x86_64-pc-windows-gnu` via the vendored `.cargo/config.toml` (mingw linker, static CRT). `compile` reads the artifact path from `cargo build --message-format=json-render-diagnostics` instead of guessing it, so workspaces and multi-bin packages work. Only registry dependencies are accepted. A `dynamic` module is scaffolded with `crate-type = ["cdylib"]` and copied next to the executable named after the gram module, not the crate (`GameLogic` → `libGameLogic.dylib` / `libGameLogic.so` / `GameLogic.dll`), so the crate keeps Rust's snake_case. Two modules may share a directory (a `CMakeLists.txt` and a `Cargo.toml` side by side); `remove --purge` then keeps the directory.
- `cmake` modules are scaffolded by `gram` (`CMakeLists.txt` + `src/main.cpp`, or for a library `include/<name>/<name>.hpp` + `src/<name>.cpp`) and built by invoking `cmake` directly (`--fresh`, `CMAKE_EXPORT_COMPILE_COMMANDS=ON`). A managed region in `CMakeLists.txt` (`# --- gram dependencies ---` markers) lets `add`/`remove` edit `FetchContent_Declare` blocks (`--url`/`--tag`) or vcpkg `find_package` calls (`--vcpkg`, needs `VCPKG_ROOT`; the generated `find_package`/`target_link_libraries` are a heuristic guess and sometimes need a manual fix — e.g. vcpkg's `vulkan` port resolves via CMake's built-in `FindVulkan` module) as text, without a real CMake parser. Windows cross-compile sets `CMAKE_SYSTEM_NAME=Windows` + the mingw compilers, statically linking the mingw runtime (`-static-libgcc -static-libstdc++ -static`) so the `.exe` runs standalone; a vcpkg module additionally gets `-DVCPKG_TARGET_TRIPLET=x64-mingw-static` (vcpkg would otherwise pick the MSVC-based `x64-windows`). vcpkg only reads the top-level manifest, so for a module with `--module-ref`s gram merges the referenced modules' `vcpkg.json` into `<build dir>/vcpkg-manifest/` and passes `VCPKG_MANIFEST_DIR`. Libraries are found whether they're static or shared and copied under their real file name. After a build, `<build dir>/shaders/` is copied next to the executable — a stopgap until modules can declare extra outputs.
- `gram` modules (`lang: "gram"`, `src: "<dir>/Gram.ron"`) are nested Gram projects: they compile nothing themselves, take no dependencies and can't be run. Module names are unique across the whole tree. `gram add --parent <gram module>` creates a module inside one.
- Either cargo or cmake supports `--module-ref`: one module depending on another (same `lang`; the referenced module must be `kind: "library"`) — a cargo path dependency, or a cmake `add_subdirectory` + `target_link_libraries` pair. Cross-language references aren't supported. Duplicate dependencies are detected by name, whatever the source.

Builds land in `build/<project>/<target>/` (plain `gram build`) or `build/<project>_<version>_<target>/` (`--ci`, one per buildable target: the host OS, plus `windows` via mingw from anywhere; `linux` ↔ `macos` is skipped with a warning). Every module of the tree lands in the root project's directory. A project's main runtime module is copied under the project's name (`Game`, `gram`), any other module under its own. Artifacts are copied as `<name>.partial` and renamed over the old file (`lang::replace_file`): rewriting a signed executable in place makes macOS SIGKILL its next launch (gram rebuilding itself, a running `Game`), and a game watching its library must never read it half-written. `gram build --module <name>` builds one module (a gram module: everything inside it); referenced modules are compiled by cargo/cmake as part of it. `gram run` executes an already-built `runtime` module's binary directly — it doesn't trigger a build.

### GramEngine (C++20, Vulkan 1.3)

`GramEngine/include/Gram/` + `src/Gram/`, built as three `STATIC` targets: `GramRenderer` (the Vulkan components, precompiled header `Gram/Renderer/Common.hpp`), `GramScripting` (the interface to loaded game modules, precompiled header `Gram/Scripting/Common.hpp`) and `GramEngine` (application, logger, platform; links both `PUBLIC`, precompiled header `Gram/Common.hpp`), so anything linking `GramEngine` gets the headers, the libraries and the PCH. Headers forward-declare where they can.

- `EntryPoint.hpp` — `main`/`WinMain` call the game's `Gram::CreateApplication(argc, argv)` (returns `std::shared_ptr<Application>`), then `Run()`.
- `Application.hpp` — the `Run()` contract. `Application/GLFWApplication` — window + main loop, a `LayerOwner`; its constructor creates and registers the `VulkanRenderer` from the `GLFWApplicationSpecification` (window, title, workspace, shader program name).
- `Layer.hpp` — `Layer<Owner>` / `LayerOwner<Owner>`: one layer per type (guarded in `RegisterLayer<T>(args...)`, constrained with C++20 `requires std::derived_from<…, Layer<GramObject>>`), started in registration order, stopped in reverse. Two owners today: `GLFWApplication` (holds `VulkanRenderer`) and `VulkanImGui` (holds `ImGuiApplicationLayer`s — the game's UI windows).
- `Renderer/` — `VulkanRenderer` coordinates RAII components that leave themselves invalid (`IsValid()`) instead of crashing: `VulkanInstance` (+ debug messenger), `VulkanSurface` (the only file that knows GLFW), `VulkanDevice` (device scoring in tiers, queue families, extensions, graphics/present queues), `VulkanSwapchain` (`Recreate()` on resize/minimize), `VulkanShader` (move-only, `vk::UniqueShaderModule`), `VulkanPipeline` (dynamic rendering), `VulkanFrame` (command buffers, two frames in flight), `VulkanImGui` (docking + multi-viewport). `UniqueObject` (no copy/move) and `MoveObject` (move-only) mark ownership. Built with `VULKAN_HPP_NO_CONSTRUCTORS` (designated initializers) and `VULKAN_HPP_NO_EXCEPTIONS`.
- `Logging/GramLogger.hpp` — spdlog-based: `GramInfo`/`GramWarning`/`GramError` (+ `GramVulkan*`), check macros that return on failure (`GramCheck` → `false`, `GramCheckVoid`, `GramVulkanCheck`/`CheckVoid`/`CheckResult`), and list markers (`GramVulkanListSelected`/`Available`/`Added`/`Missing`, `GramVulkanListItem`). `GramCheck(x)` reads like an assert: it fails when `x` is false.
- `Platform.hpp` — `GetExecutableDirectory()` (`GetModuleFileNameW` / `/proc/self/exe` / `_NSGetExecutablePath`; `argv[0]` is wrong under WSL interop), `GetDynamicLibraryFileName("GameLogic")` (`libGameLogic.dylib` / `.so` / `GameLogic.dll`) and `DynamicLibrary` (`UniqueObject` over `dlopen`/`LoadLibraryW`: `IsValid()`, `FindSymbol<T>(name)`, unloads in its destructor; loader errors are logged, never thrown).
- `Scripting/` — the engine side of the game contract, the same for every game. `HostAPI.hpp` (`Host` — an opaque context pointer Rust passes back —, `Log`, `RegisterSystem`, `GetComponent`); `GameAPI.hpp` (`GameAPILoader`, an application layer taking the `World&`: the `GameAPI` table (`Version`, `OnLoad`, `OnUnload`, `RunSystem`) and `GameAPIVersion` (3), its own `HostAPI` with `Host = this`, the system registry, the event queue (`Emit(name, target)`), copy-on-load and reload); `ECS/ObjectID.hpp` (`ObjectID` = index + generation, `InvalidObjectID`); `ECS/World.hpp` (`World`, an application layer registered before the loader: entity slots with a generation bumped on destroy and a free list, so a stale `ObjectID` is detected (`IsAlive`); one `ComponentStorage` per component type — packed bytes, `Owners`, `SlotOf` — with `AddComponent`/`GetComponent` and swap-remove on destroy; component addresses move when storage grows, so Rust only gets one for the duration of a call); `ECS/System.hpp` (`System::Stage` (`Update`/`Event`), `System::Descriptor` (name, stage, event, index), `System::Context` (`DeltaTime`, `Time`, `EventTarget`)); `ECS/Component.hpp` (`ComponentID` = `uint64_t`, `ComponentIDFromName` (constexpr 64-bit FNV-1a of the name, the same `const fn` in `gram-core`), `FieldDescriptor` / `ComponentDescriptor` (with its `ID`), what the generic ImGui inspector draws a component from). `LogLevel` (`uint32_t`) lives in `GramLogger.hpp`, outside the `GRAM_LOGGER_ENABLED` fence. Every type crossing to Rust uses fixed-size fields only.
- `Editor/` — the start of a small editor: ImGui panels that are the same for every game, in the `GramEngine` target, fenced with `GRAM_IMGUI_ENABLED`. An ImGui layer always returns `true` from `OnDrawFrame` (`false` would skip the layers after it), a closed panel just stops drawing. `InspectorPanel` (takes the `World&`; `Select(entity)`) draws every component of the selected entity from its descriptor through `World::ForEachComponent`, one widget per `FieldDescriptor::FieldType`; `SystemsPanel` (takes the `GameAPILoader&`) has the Reload button and reads `GameAPILoader::GetSystems()`.
- `Common.hpp` — platform and feature macros: Apple/MoltenVK-only code is fenced with `GRAM_PLATFORM_APPLE`; capabilities such as `GRAM_GEOMETRY_SHADERS` are derived from the platform here, and renderer code tests the feature macro, not the platform.
- Shaders: `GramShaders.cmake` provides `gram_add_hlsl_shader(<target> <source>)`, compiling a `.hlsl` file (a path relative to the caller's `CMakeLists.txt`) (entry points `VSMain`/`PSMain`) with the Vulkan SDK's `dxc` into `<top-level build dir>/shaders/<name>.{vert,frag}.spv`. The shaders belong to the game (`Game/Content/shaders/`); the engine only owns the tooling.
- Dependencies (root `Gram.ron`): vcpkg `vulkan` (headers only off Windows — the loader comes from the system/Vulkan SDK), `glfw3`, `glm`, `imgui` (features `glfw-binding`, `vulkan-binding`, `docking-experimental`), spdlog via FetchContent.

`Game/Runtime/src/main.cpp`: `RuntimeApplication : GLFWApplication` registers a `World` and a `GameAPILoader` (from `GramEngine`) for `GameLogic`, creates one entity with a `Greeting` component (data in the `World`), then registers the editor panels (after them: the panels keep references) and selects that entity in the inspector. Its own `GameUI` window only has the Greet button, emitting `"greet"` targeting that entity. `Greeting` is described once in `Game/Content/scripts/greeting.ron`; its C++ struct + descriptor live in `Game/Content/Components.generated.hpp` (the runtime adds `Content/` to its include path) (header-only, `inline` descriptors) and its Rust struct + `impl Component` in `Game/Content/components.generated.rs` (`#[path]` module `components`). Both are generated by `gram build` (not checked in: plain `cargo` on a fresh clone needs one `gram generate` first); a new field shows up in the inspector without C++ changes, as long as its `FieldDescriptor::FieldType` has a case there. `CreateApplication` only fills the application spec.

Systems (steps 1–2 of `docs/wave-1-systems-design.md`, done 2026-11-02): the game's systems are plain Rust functions (`gram_core::system::System = fn(&Context)`) listed in `Game/Content/lib.rs` through `gram_core::export_game! { events: {…}, update: […] }`, which builds the `system::Entry` list (stage, name, event, function). `on_load` calls `gram_core::system::register(SYSTEMS)`, which sends one `Descriptor` per entry (index = position in the list) through `HostAPI::RegisterSystem`; C++ keeps copies in its registry, cleared before every unload. Each frame `GameAPILoader::OnDrawFrame` fills a `System::Context`, runs every `Update` system through `GameAPI::RunSystem(index, ctx)` (Rust's single dispatcher, inside `guard`), then hands each queued event to the systems registered for it; the queue is emptied every frame, loaded library or not. Adding a system is one name in `export_game!`: no C++ change, no version bump, picked up by a reload. An event system gets its target through `ctx.event_target()`, and reaches a component with `ctx.with::<T>(id, |c| …)` / `ctx.with_mut::<T>(…)` (step 3, done 2026-11-02): `HostAPI::GetComponent(entity, T::ID)` → the address, lent to the closure only; `None` for a dead entity or a missing component. Overlapping borrows are caught like a `RefCell` (step 5): `gram_core::borrow::BorrowGuard` keeps the active borrows in a `thread_local!` list (two reads may overlap; a write conflicts with anything on the same entity + component), panics with the caller's location (`#[track_caller]`, the panic outside the list's closure), and releases in `Drop`, so a system that panics doesn't leave its borrow behind. Verified: text edited in the inspector survives reloads, and Rust reads and writes it.

Reload: every 0.5 s `GameAPILoader::OnDrawFrame` compares the original library's write time with the last loaded one; on change `Reload()` runs `OnUnload`, unloads, copies under a new name (a new name each time, since macOS may not really unload a Rust dylib) and loads it again. A loader layer's `OnDrawFrame` always returns `true`: a failed reload means no Rust logic, not quitting. Panics never cross the boundary: each exported function's body runs inside `gram_core::guard(f) -> Option<R>` (`catch_unwind`), and the panic hook `gram_core::init` installs logs `file:line:col: message` through the host instead of stderr. The contract types (`HostAPI`, `GameAPI`, `System::*`) are written twice by hand (C++, and Rust in `gram-core`: `game_api`, `system`), checked with size asserts on both sides; field order is the binary contract.

## Non-goals (current)

- No multiplayer/networking, no visual editor, no emulators/plugins — noted ideas, not now.
- No performance/optimization focus — functional correctness first.
- **Cross-compilation is scoped to `--ci` builds only** (added 2026-09-09): a `gram build --ci` iterates every target in `ModuleConfig.targets` (`linux`/`windows`/`macos`, skipping what the host can't build: `windows` cross-compiles via mingw from anywhere, `linux` ↔ `macos` doesn't); a plain `gram build` only compiles for the host it's run on, and `--target` builds a single target. Wave 1's native deps (Vulkan, GLFW, ImGui) cross-compile to Windows through vcpkg's `x64-mingw-static` triplet. In practice: develop on macOS, `gram build --ci` there, run the `.exe` natively on Windows and build Linux in WSL2.
- **No CI/CD until an explicit "Personal Builds" stage.** Planned design when that starts: GitHub Actions (free hosted runners) run classic Rust CI (`cargo build`/`test`/`clippy`) on every push; only on success, one step uses `tailscale/github-action` (ephemeral, ACL-scoped tailnet node, no exposure) to reach the private network and either mirror to Gitea (triggers the existing Jenkins webhook) or call Jenkins directly. A permanent self-hosted GitHub Actions runner was considered and rejected — it works (outbound-poll only, no port to open) but needs an ongoing-maintained process; the hosted-runner + ephemeral-Tailscale-hop design needs nothing running when idle.

## Repo model

Gitea gets added later only as an automatic pull-mirror of GitHub, once "Personal Builds" actually starts — not before.
