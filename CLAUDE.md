# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It is self-contained: this repo is meant to be cloned standalone on dev machines (Windows, macOS) that don't have the author's Obsidian vault or the `Projects` monorepo it's normally a submodule of — don't assume either is available. Current task-level progress lives in `.gram.kanban.md`; check it first.

## What this is

Gram — a personal game engine (Rust + C++), started from rediscovered passion, not a portfolio obligation. No deadline. Structured in "waves": each wave produces one working artifact plus a devlog post (`petretiberiu.dev`).

## Waves

- **Wave 0 — Gram Build** (done): a pure-Rust CLI build tool — no C++, no runtime deps. Full command set: `gram init`/`build`/`add`/`remove`/`run`, driving a `Gram.ron` project file (serde + `ron-rs`, a format reused later for asset definitions). A `cargo` module kind delegates straight to real `cargo`; a `cmake` module kind scaffolds a C++ project with FetchContent/vcpkg dependency resolution, for when Wave 1 needs it. The project is self-hosting (`gram` builds itself via its own `Gram.ron`). Details: `docs/wave-0-*.md`.
- **Wave 1 — Hello Triangle**: window + Vulkan + triangle + ImGui, C++/Rust interop. C++ owns `main()`, the renderer and **all state** (entities, components, IDs; never reloaded). Rust gameplay logic is a single `cdylib` (gram module `GameLogic`, crate `game-logic` in `Game/Content/`, built as `libGameLogic.dylib`) with no game state of its own, loaded/reloaded via `LoadLibrary`/`dlopen` (copy-on-load) and called through plain `extern "C"`: two `#[repr(C)]` function tables, `HostAPI` (filled by C++, what the engine offers) and `GameAPI` (filled by Rust, what the game offers), exchanged through the one exported symbol `game_get_api`. Shared data is `#[repr(C)]` in host memory, reached from Rust through IDs (`Handle`/`Reference`). `gram/gram-core` is an `rlib` holding the library's side of the contract, in two halves. `interop/` is the FFI plumbing: `host` (`HostAPI`, `init` — stores a copy of the host table, installs the panic hook —, `host()`, `guard` (`catch_unwind`)), `logging` (`LogLevel`, `log`, the `info!`/`trace!`/`warn!`/`error!` macros) and `game` (the `GameAPI` table, `GAME_API_VERSION`, `export_game!`: a `macro_rules!` taking `events: { "name" => [systems] }` and `update: [systems]`, generating the system list, `on_load`/`on_unload`/`run_system`, the `GameAPI` table and `game_get_api` inside a `mod __gram_export`, naming everything through `$crate::`). `scripting/` is what a script sees: `system` (`context`: `Stage`, `Descriptor`, `Context` with `with`/`with_mut`, `Entry`, `register`; `query`: `Query<'a, T>`; `params`: `SystemParam`, `IntoSystem`, `EventTarget`/`Time`/`DeltaTime`), `types::Str<N>` (a `#[repr(transparent)]` fixed `\0`-terminated text buffer: `new`/`set`/`as_str`), `world::ObjectID`, `component` (`ComponentID`, `component_id`, `trait Component`) and `borrow::BorrowGuard`. `prelude` lists by name (no globs) only what a system uses: `Context`, `Query`, `EventTarget`, `Time`, `DeltaTime`, `Str`, `ObjectID`, the log macros and `export_game!`. `codegen` (`#[doc(hidden)]`) is the generated code's own list (`use gram_core::codegen::*;`: `Component`, `ComponentID`, `component_id`, `Str`), kept apart from the scripts' prelude; a new schema field type adds its Rust type there. No exported functions, no game state (the stored host table is copied into each loaded library, being an `rlib`). No `bevy_ecs`, no `cxx`/Corrosion (adopted 2026-10-28). Components are described in `.ron` schemas from which `gram build` generates the Rust struct, the C++ struct and a descriptor table (like Anvil's `.mold`); a schema change needs a rebuild + restart, a Rust logic change only a reload. Proof of concept: a `Greeting` component with one text field, edited in an ImGui inspector, surviving a reload — no sphere in Wave 1. Details: `docs/wave-1-rust-interop.md` (as built), designs in `docs/wave-1-rust-gameplay-design.md` and `docs/wave-1-systems-design.md`.
- **Wave 2 — Ray Tracer**: Vulkan compute shader pipeline; spheres first owned by C++, then driven by Rust entities (position/color/radius).
- **Wave 3+**: raster pipeline, post-processing, asset manager, world serialization — noted, unplanned.

## Methodology — who writes what

- **User writes**: anything that's a new skill being learned for the first time (a CLI with subcommands the first time, Vulkan code following the official tutorial, ECS entity/component/system definitions) — the parts with real learning value.
- **Claude Code writes**: scaffolding (CLI boilerplate, build system wiring, Rust↔C++ interop glue, CMake setup) — plumbing without learning value, once a pattern is already familiar.
- Rule of thumb: first time doing something new → user writes it. Something done many times before (Cargo.toml config, adding a dependency) → delegate to Claude Code.

## Commands

The `gram` crates live in a cargo workspace at `gram/Cargo.toml` (`gram-cli`, package `gram`, plus the `gram-common` library), not the repo root, so plain `cargo` needs `--manifest-path` (or `cd gram` first):

- Build: `cargo build --manifest-path gram/Cargo.toml`
- Run: `cargo run --manifest-path gram/Cargo.toml -- <args>` (e.g. `-- --help`, `-- init hello-world`)
- Test: `cargo test --manifest-path gram/Cargo.toml` — command-level tests in `gram/gram-cli/tests/` (one file per subcommand plus `nested.rs`; read `tests/support/mod.rs` first). They run the real binary in a temp sandbox, kept on failure. The `build`/`run` tests need cmake and a C++ compiler; one test needs crates.io and is `#[ignore]`d.
- Self-hosted (once bootstrapped): from the repo root, `gram/target/debug/gram build` (or `build --ci`, `build --module GameLogic`, `run`) builds the whole tree from the checked-in root `Gram.ron` — `gram` itself, `GramEngine` and the game. The tool's own artifact lands as `build/<project>/<target>/<config>/gram`.

## Architecture (current)

The repo is a Gram project tree. Root `Gram.ron` (`gram-engine`, `main: "Runtime"`) holds three modules: `gram` (a nested project → `gram/Gram.ron`: `gram-cli` runtime + `gram-common` library), `GramEngine` (cmake, `STATIC` library) and `Game` (a nested project → `Game/Gram.ron`: `Runtime` → `Game/Runtime/`, cmake runtime, `Module(name: "GramEngine")`; `GameLogic` → `Game/Content/Cargo.toml`, cargo `dynamic`, `Module(name: "gram-core")`). The game is laid out like a Unity project: `Runtime/` is the thin C++ entry point, `Content/` holds what the game is made of (the crate root `lib.rs` at its top, `[lib] path = "lib.rs"`, so scripts can sit in folders next to their data; the shaders in `Content/shaders/`; later schemas and scenes), each kind of file built by its own tool for now. `gram/Gram.ron` also holds `gram-core` (cargo library), the Rust half of the engine's scripting contract.

### Gram Build (`gram/`)

Rust, edition 2024, `clap` (derive) + `serde`/`ron-rs`. `gram-cli/src/main.rs` only parses and prints outcomes; everything else is in `gram-common/src/`:

- `commands/` — clap structs (`Cli`, `InitCommand`, `BuildCommand`, `AddCommand`, `RemoveCommand`, `RunCommand`, `GenerateCommand`, `IdeCommand`) plus thin functions calling `BuildConfig` (see `README.md` for the flag reference).
- `config/mod.rs` — `BuildConfig`, the `Gram.ron` project: `open`/`write` (nested `Gram.ron` files are loaded into one flat module list and split back on write), module add/remove, `build`/`run` over modules, `resolve`/`module_refs` (→ `ResolvedModule`), `artifact_name`, and `add_dependency` returning an `AddOutcome` (`ModuleCreated`/`TargetsAdded`/`DependencyAdded`/`AlreadyPresent`/`NothingToDo`). The CLI decides what to print; the core only reports.
- `config/ide.rs` — `gram ide xcode|vs`: `ide_roots` (the cmake modules no other cmake module references), `ide_sources` (the files shown but not compiled: the cmake modules' headers, each on the target compiling the sources next to it (`gram_ide_headers`), the Rust dynamic modules' and their references' `.rs`/`.ron`/`.toml`/`.hlsl`, globbed by CMake with `CONFIGURE_DEPENDS`), `superproject` (written by the user: the generated `CMakeLists.txt` — `add_subdirectory` of the roots, an `add_custom_target(<name> ALL COMMAND gram build --module <name> --config $<LOWER_CASE:$<CONFIG>>)` per cargo `dynamic` module, each runtime root's `OUTPUT_NAME`/`RUNTIME_OUTPUT_DIRECTORY` set to where `gram build` puts it and `add_dependencies` on the dynamic modules) and `ide`, which writes it to `build/ide/<ide>/` and configures it like a module (the configurations, vcpkg with the roots' merged manifest) with `-G Xcode` (plus `CMAKE_OSX_ARCHITECTURES` = the host's, `CMAKE_XCODE_GENERATE_SCHEME`, and `DEVELOPER_DIR` when `xcode-select` points at the Command Line Tools) or Visual Studio (`Visual Studio 18 2026` with msvc's `ToolchainSettings`: `-A x64`, the static CRT, `x64-windows-static`; writes `gram-engine.slnx`, opened by `--open`; `VS_STARTUP_PROJECT` = the first runtime root; the baked `PATH` escaped as `\\` + `$<SEMICOLON>`; the shown files `HEADER_FILE_ONLY` + `VS_TOOL_OVERRIDE "None"`, or Visual Studio compiles the `.hlsl` ones with FXC). Visual Studio doesn't build while it debugs, so hot reload there goes through the editor's Play button (`docs/gram-windows-visual-studio.md`).
- `config/module.rs` — `ModuleConfig` (`name`, `lang`: `"cargo"`|`"cmake"`|`"gram"`, `kind`: `"runtime"`|`"library"`|`"dynamic"` (cargo only: a `cdylib`), `src`, `deps: Vec<DependencySpec>`, `targets`: `"linux"`|`"windows"`|`"macos"`, plus a `#[serde(skip)]` field remembering its project file), the language-independent build steps and `dir()` (the parent of `src`).
- `lang/mod.rs` — the `ModuleBackend` trait (`manifest_file`, `scaffold`, `compile`, `artifact_naming`, `add_dependency`, `rm_dependency`, `add_module_ref`, `rust_analyzer_manifest`), `backend_for(lang)` — the only place that matches on the `lang` string —, `DependencySpec` (`Registry{name}`/`Git{name,url,tag}`/`Vcpkg{name}`/`Module{name}`, serialized as-is into `Gram.ron`) and `ResolvedModule` (computed at runtime, never serialized: `dir` relative to the project root, `rel_dir` relative to the consumer).
- `lang/cargo.rs`, `lang/cmake.rs`, `lang/gram.rs` — the three zero-sized backends. `lang/vcpkg.rs` — helpers used by cmake (manifest read/write, merging referenced modules' manifests); vcpkg is a dependency source, not a module language.
- `schema/` — component schemas: `find` (the `.ron` files starting with `Component(` under a module, skipping `target/`/`build*/`), `write_if_changed`, and `generate(&[SchemaFile]) -> Generated { rust, cpp }` — the generator proper (written by the user): the serde model (`Component`, `Field`, `FieldType`: `Str(N)`/`F32`/`I32`/`U32`/`Bool`/`Vec3` (C layout: 12 bytes, align 4; `gram_core::Vec3` in Rust, `glm::vec3` in C++, a `DragFloat3` in the inspector)), `Component::layout` (C's offset/size rules, = `#[repr(C)]`) and the two emitters; C++ field names are the schema's snake_case in PascalCase; each C++ struct also gets `static constexpr ComponentID ID` and `static const ComponentDescriptor& Descriptor()` (defined after its descriptor), for `World`'s typed access. `BuildConfig::generate(module)` runs it per cargo module and writes `components.generated.rs` / `Components.generated.hpp` next to the `Cargo.toml`, only when their content changed; `gram build` runs it for the whole tree before compiling anything (a cmake module may include a cargo module's header). The generated files are git-ignored (`*.generated.*`).
- `pass/` — render passes described once in `.ron` files starting with `Pass(` (anywhere in the module; the game keeps them next to their shaders, `Content/shaders/<Name>.pass.ron`): `name`, `stage` (`Raster`: `VSMain`/`PSMain` · `Compute`: `CSMain`), an optional `shader` path (default `<name>.hlsl` next to the `.ron`), `uniform` (fields of `GpuType`: `F32`/`I32`/`U32`/`Vec2`/`Vec3`/`Vec4`/`Mat4` (`glm::mat4` / `float4x4`, column after column on both sides, 64 bytes from a 16-byte boundary)), `buffers` (`Buffer(name, element, fields)`: a `StructuredBuffer<element>`), `inputs` (`Sampled(name, ty)`: a combined image sampler) and `outputs` (`Storage(name, format)`: an `RWTexture2D`). Bindings by convention: set 0 = the uniform at 0 (when it has fields), then the buffers; set 1 = the inputs, then the outputs. `layout` (written by the user) lays every struct out by GPU rules (vec3/vec4 at 16, vec2 at 8, scalars at 4, size a multiple of 16) with explicit `_PadN` fields, so both sides are the same bytes whatever rules dxc applies. `generate` → `GeneratedPasses { cpp, cmake, hlsl }`: `Passes.generated.hpp` next to the `Cargo.toml` (per pass `<Name>Params` with the uniform's fields, `Shader`, `InputCount`/`OutputCount` and a `<Resource>Binding` constant per named resource, plus each buffer's element struct; size/offset asserts), `<shader>.generated.hlsli` next to each shader (the same structs, offsets as comments, and every `[[vk::binding]]` declaration: `Params`, the buffers, `<Input>`/`<Input>Sampler`, the outputs) and `Shaders.generated.cmake` (`gram_add_content_shaders(<target>)`: one `gram_add_hlsl_*_shader` per pass). `BuildConfig::generate` runs it next to the component schemas.
- `target.rs` — `SUPPORTED_TARGETS`, `validate_targets`. `toolchain.rs` — `Toolchain` (`native`/`mingw`/`msvc`, `--toolchain`), `resolve(host, target, requested, installed)` (the candidates for (host, target), preferred first: same-OS unix `[Native]`, unix→windows `[Mingw]`, windows→windows `[Msvc, Mingw]`; the first installed one, with `fell_back_from` when it isn't the first, warned about by `ModuleConfig`; an explicit toolchain never falls back), `installed` (a `PATH` lookup; msvc also through `visual_studio()`, which asks vswhere once) and `settings` → `ToolchainSettings` (generator, cmake args, vcpkg triplet, cargo triple), the only place that knows mingw's compilers, triplet and static runtime and msvc's (`Visual Studio 18 2026`, `-A x64`, `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded$<$<CONFIG:Debug>:Debug>`, `x64-windows-static`: a static CRT on both sides); the backends' `compile` takes it. `cmake()` is the one place cmake is started from: the `PATH`'s, else the one Visual Studio ships, else a clear error (so gram works from a plain PowerShell). `directory.rs` — `Directory` file I/O. `vscode.rs` — `write_vscode_settings` (merges into an existing `settings.json`).

gram's cwd is always the project root: `cargo add --path` takes a root-relative path (`ResolvedModule::dir`), cmake's `add_subdirectory` a consumer-relative one (`rel_dir`).

Module language behavior:
- `cargo` modules delegate straight to real `cargo` (`init`/`add`/`rm`/`build`), including cross-compiling to `x86_64-pc-windows-gnu` via the vendored `.cargo/config.toml` (mingw linker, static CRT). `compile` reads the artifact path from `cargo build --message-format=json-render-diagnostics` instead of guessing it, so workspaces and multi-bin packages work. Only registry dependencies are accepted. A `dynamic` module is scaffolded with `crate-type = ["cdylib"]` and copied next to the executable named after the gram module, not the crate (`GameLogic` → `libGameLogic.dylib` / `libGameLogic.so` / `GameLogic.dll`), so the crate keeps Rust's snake_case. Two modules may share a directory (a `CMakeLists.txt` and a `Cargo.toml` side by side); `remove --purge` then keeps the directory.
- `cmake` modules are scaffolded by `gram` (`CMakeLists.txt` + `src/main.cpp`, or for a library `include/<name>/<name>.hpp` + `src/<name>.cpp`) and built by invoking `cmake` directly (`--fresh`, `CMAKE_EXPORT_COMPILE_COMMANDS=ON`). A managed region in `CMakeLists.txt` (`# --- gram dependencies ---` markers) lets `add`/`remove` edit `FetchContent_Declare` blocks (`--url`/`--tag`) or vcpkg `find_package` calls (`--vcpkg`, needs `VCPKG_ROOT`; `vcpkg.json` is rewritten keeping object entries (`{ "name", "platform", "features" }`) and unmanaged fields; the generated `find_package`/`target_link_libraries` are a heuristic guess and sometimes need a manual fix — e.g. vcpkg's `vulkan` port resolves via CMake's built-in `FindVulkan` module) as text, without a real CMake parser. Windows cross-compile sets `CMAKE_SYSTEM_NAME=Windows` + the mingw compilers, statically linking the mingw runtime (`-static-libgcc -static-libstdc++ -static`) so the `.exe` runs standalone; a vcpkg module additionally gets `-DVCPKG_TARGET_TRIPLET=x64-mingw-static` (vcpkg would otherwise pick the MSVC-based `x64-windows`). vcpkg only reads the top-level manifest, so for a module with `--module-ref`s gram merges the referenced modules' `vcpkg.json` into `<build dir>/vcpkg-manifest/` and passes `VCPKG_MANIFEST_DIR`. Libraries are found whether they're static or shared and copied under their real file name. After a build, `<build dir>/shaders/` and `<build dir>/textures/` are copied next to the executable — a stopgap until modules can declare extra outputs.
- `gram` modules (`lang: "gram"`, `src: "<dir>/Gram.ron"`) are nested Gram projects: they compile nothing themselves, take no dependencies and can't be run. Module names are unique across the whole tree. `gram add --parent <gram module>` creates a module inside one.
- Either cargo or cmake supports `--module-ref`: one module depending on another (same `lang`; the referenced module must be `kind: "library"`) — a cargo path dependency, or a cmake `add_subdirectory` + `target_link_libraries` pair. Cross-language references aren't supported. Duplicate dependencies are detected by name, whatever the source.

`gram build --config debug|release|final` (default `debug`; `gram run --config` the same) picks the configuration: `profile.rs`'s `Profile` maps it to the cmake build type (`Debug`/`Release`/`Final`, one build dir per target and config: `build-<target>-<config>`) and to cargo's `--release` plus `CARGO_PROFILE_RELEASE_*` overrides (Release keeps symbols; Final turns on LTO and strip), with no `[profile]` section in any `Cargo.toml`. CMake learns the configurations from `gram-common/src/lang/cmake/GramConfigurations.cmake` + `GramConfigurationFlags.cmake` (embedded with `include_str!`, written to `<build dir>/gram/`, passed as `CMAKE_PROJECT_TOP_LEVEL_INCLUDES`): the first runs at the top-level `project()` before the compiler is known (`CMAKE_CONFIGURATION_TYPES`, LTO for Final through `CMAKE_INTERPROCEDURAL_OPTIMIZATION_FINAL`, `CMAKE_MAP_IMPORTED_CONFIG_FINAL "Release;"` so Final links vcpkg's release libraries and `FindVulkan`'s config-less target) and registers the second as `CMAKE_USER_MAKE_RULES_OVERRIDE`, which derives the `_INIT` flags from the compiler's own (Final = Release's, Release = RelWithDebInfo's). Builds land in `build/<project>/<target>/<config>/` (plain `gram build`) or `build/<project>_<version>_<target>_<config>/` (`--ci`, one per buildable target: the host OS, plus `windows` via mingw from anywhere; `linux` ↔ `macos` is skipped with a warning). Every module of the tree lands in the root project's directory. A project's main runtime module is copied under the project's name (`Game`, `gram`), any other module under its own. Artifacts are copied as `<name>.partial` and renamed over the old file (`lang::replace_file`): rewriting a signed executable in place makes macOS SIGKILL its next launch (gram rebuilding itself, a running `Game`), and a game watching its library must never read it half-written. After building a `dynamic` module for this machine (not `--ci`), gram writes `<module>.gram-build` next to it: how the editor's Play button builds it again (one `<key> <value>` per line: `dir`, `env PATH=...`, `arg`s, the program first). `gram build --module <name>` builds one module (a gram module: everything inside it); referenced modules are compiled by cargo/cmake as part of it. `gram run` executes an already-built `runtime` module's binary directly — it doesn't trigger a build.

### GramEngine (C++20, Vulkan 1.3)

`GramEngine/include/Gram/` + `src/Gram/`, built as three `STATIC` targets: `GramRenderer` (the Vulkan components, precompiled header `Gram/Renderer/Common.hpp`), `GramScripting` (the interface to loaded game modules, precompiled header `Gram/Scripting/Common.hpp`) and `GramEngine` (application, logger, platform; links both `PUBLIC`, precompiled header `Gram/Common.hpp`), so anything linking `GramEngine` gets the headers, the libraries and the PCH. Headers forward-declare where they can.

- `EntryPoint.hpp` — `main`/`WinMain` call the game's `Gram::CreateApplication(argc, argv)` (returns `std::shared_ptr<Application>`), then `Run()`.
- `Application.hpp` — the `Run()` contract. `Application/GLFWApplication` — window + main loop, a `LayerOwner`; its constructor creates and registers the `VulkanRenderer` from the `GLFWApplicationSpecification` (window, title, workspace); the game adds its render passes to it (`AddPass`), the engine knows none of its shaders.
- `Layer.hpp` — `Layer<Owner>` / `LayerOwner<Owner>`: one layer per type (guarded in `RegisterLayer<T>(args...)`, constrained with C++20 `requires std::derived_from<…, Layer<GramObject>>`), started in registration order, stopped in reverse. Two owners today: `GLFWApplication` (holds `VulkanRenderer`) and `VulkanImGui` (holds `ImGuiApplicationLayer`s — the game's UI windows).
- `Renderer/` — `VulkanRenderer` coordinates RAII components that leave themselves invalid (`IsValid()`) instead of crashing: `VulkanInstance` (+ debug messenger), `VulkanSurface` (the only file that knows GLFW), `VulkanDevice` (device scoring in tiers, queue families, extensions, graphics/present queues), `VulkanSwapchain` (`Recreate()` on resize/minimize), `VulkanShader` (move-only, `vk::UniqueShaderModule`), `VulkanPipeline` (dynamic rendering), `VulkanFrame` (command buffers, two frames in flight, `Begin`/`End`, the swapchain image's transitions), `VulkanImage` (an owned image + memory + view + sampler; `Load(device, path)` uploads an image file through a staging buffer, `stb_image` compiled only here; `VulkanImage::State` tracks an image's last use and `Transition` emits the barrier to the next, also for the swapchain's images), `VulkanBuffer` (`Create<Kind>`: a `BufferKind` concept over kind structs — `VertexBuffer`/`IndexBuffer` staged into device-local memory, `UniformBuffer<T>`/`StorageBuffer<T>` host-visible, one per frame in flight; `Map<T, Access>()` returns a move-only token that unmaps in its destructor), `VulkanDescriptors` (one set layout from a pass's bindings, its pool and `setCount` sets; `Write` points a binding at per-frame buffers or an image, once, at creation), `VulkanRenderTarget` (the scene image: resized on request at the start of a frame, after a `waitIdle`), `VulkanPass` (what `AddPass` takes: `Record` into the frame's command buffer), `VulkanImGui` (docking + multi-viewport; itself the last pass), `VulkanProfiler` (one timestamp query pool per frame in flight: `BeginFrame` reads the slot's last results once its fence was waited for and resets it, `Begin`/`End` write a timestamp around each pass's `Record` (only between `VulkanFrame::Begin` and `End`), smoothed per `VulkanPass::GetName()`; `VulkanDevice` keeps the chosen device's `timestampPeriod` and valid bits; shown by the editor's `Engine/Profiler` panel), `VulkanPresentPass` (whenever the editor's Viewport isn't there, i.e. Release and Final, before ImGui when there is one: asks the scene target for the swapchain's size and blits it into the swapchain image, `eNearest`; `VulkanFrame::MarkSwapchainWritten` keeps `End` from clearing it; hence `eTransferDst` on the swapchain's images and `eTransferSrc` on the scene target). `UniqueObject` (no copy/move) and `MoveObject` (move-only) mark ownership. Built with `VULKAN_HPP_NO_CONSTRUCTORS` (designated initializers) and `VULKAN_HPP_NO_EXCEPTIONS`.
- `Logging/GramLogger.hpp` — spdlog-based: `GramInfo`/`GramWarning`/`GramError` (+ `GramVulkan*`, and `Editor*` for the game's messages outside a system), every logger also writing to a 1000-message `ringbuffer_sink` the editor reads back (`GetEditorMessages()` → `last_raw()`); the list logger is named `Vulkan.List` (`ListLoggerSuffix`), and each game system gets its own logger `System.<name>` (`GetSystemLogger`, created on first use), which the loader's `HostAPI::Log` uses while that system runs (`s_RunningSystem` in `GameAPI.cpp`, set around `RunSystem`: `Log` has no host pointer); check macros that return on failure (`GramCheck` → `false`, `GramCheckVoid`, `GramVulkanCheck`/`CheckVoid`/`CheckResult`), and list markers (`GramVulkanListSelected`/`Available`/`Added`/`Missing`, `GramVulkanListItem`). `GramCheck(x)` reads like an assert: it fails when `x` is false.
- `Platform.hpp` — `GetExecutableDirectory()` (`GetModuleFileNameW` / `/proc/self/exe` / `_NSGetExecutablePath`; `argv[0]` is wrong under WSL interop), `GetDynamicLibraryFileName("GameLogic")` (`libGameLogic.dylib` / `.so` / `GameLogic.dll`) and `DynamicLibrary` (`UniqueObject` over `dlopen`/`LoadLibraryW`: `IsValid()`, `FindSymbol<T>(name)`, unloads in its destructor; loader errors are logged, never thrown), `ReadProcessCommand(path)` (a `.gram-build` file → `ProcessCommand { Directory, Environment, Arguments }`) and `RunProcess(command, onLine)` (blocking, for a worker thread: `CreateProcessW` with a pipe and no console window / `posix_spawn`; every output line to the callback; the exit code, -1 when it couldn't start; the POSIX branch not compiled yet as of 2026-11-16).
- `Scripting/` — the engine side of the game contract, the same for every game. `HostAPI.hpp` (`Host` — an opaque context pointer Rust passes back —, `Log`, `RegisterSystem`, `GetComponent`, and `GetComponentCount`/`GetComponentAt`: one component type walked by position, storage order, the owner written through a pointer; size-asserted as 6 pointers on both sides); `GameAPI.hpp` (`GameAPILoader`, an application layer taking the `World&`: the `GameAPI` table (`Version`, `OnLoad`, `OnUnload`, `RunSystem`) and `GameAPIVersion` (4), its own `HostAPI` with `Host = this`, the system registry, the event queue (`Emit(name, target)`), copy-on-load and reload, and the play state: `ReplayState { Stopped, Building, Playing, Paused }`, a state machine changed only by `Play()` (reads the `.gram-build` next to the library, runs it through `RunProcess` on a `std::async` thread polled each frame, reloads on success, then Playing; from Stopped it takes the `World` snapshot; while Playing it rebuilds without stopping), `Pause()`, `Stop()` (restores the snapshot) and `FinishBuild()`; systems run only while playing, `Context::Time` counts only that time; Debug starts Stopped, Release/Final play from the start); `ECS/ObjectID.hpp` (`ObjectID` = index + generation, `InvalidObjectID`); `ECS/World.hpp` (`World`, an application layer registered before the loader: entity slots with a generation bumped on destroy and a free list, so a stale `ObjectID` is detected (`IsAlive`); `ECS/Component.hpp` (`ComponentID` = `uint64_t`, `ComponentIDFromName` (constexpr 64-bit FNV-1a of the name, the same `const fn` in `gram-core`), `FieldDescriptor` / `ComponentDescriptor` (with its `ID`), what the generic ImGui inspector draws a component from). `LogLevel` (`uint32_t`) lives in `GramLogger.hpp`, outside the `GRAM_LOGGER_ENABLED` fence. Every type crossing to Rust uses fixed-size fields only.
- `Editor/` — the start of a small editor, in the `GramEngine` target. Panels have an owner (`PanelOwner::Engine`/`Game`): the engine's (the same for every game: Outliner, Inspector, Systems, Log, Viewport) are fenced with `GRAM_EDITOR_ENABLED` (Debug only, where the game is written), a game's own (`AddPanel<T>(args...)`, or `AddPanel(path, draw)`: a `FunctionPanel` whose contents a function draws, no subclass; all of them drawn by the one `EditorFunctionPanels` layer, since a `LayerOwner` takes a single layer per type) with `GRAM_IMGUI_ENABLED` (Debug and Release, where it's tested); Final has neither. `Editor` (created by the game after the `World` and the loader, since the engine's panels keep references) registers `EditorToolbar` (Debug only: Play/Pause/Stop driving the loader's `ReplayState`, a `BeginViewportSideBar` strip under the menu bar, registered right after it; icons drawn with the draw list), `EditorMenuBar` (main menu: an `Engine` and a `Game` menu, each shown only when it has panels, reopening closed ones; the frame rate, right-aligned) and the panels as ImGui layers. Without the editor (Release) there's no Viewport, so `VulkanPresentPass` blits the scene into the swapchain and ImGui draws the game's panels over it (the dockspace is passthru). Every panel derives from `EditorPanel` (a path, `"Debug/Ray Tracer"`: the submenus under its owner's menu, the window's title (the last segment) and its ImGui ID (the whole path, `Title###Path`); an open flag, `DrawContents()`; its `OnDrawFrame` always returns `true`, since `false` would skip the layers after it). `OutlinerPanel` lists the live entities (`World::ForEachEntity`) and selects into `InspectorPanel`, which draws every component of the selection from its descriptor (`World::ForEachComponent`), one widget per `FieldDescriptor::FieldType`. `LoggerPanel` ("Log", only with `GRAM_LOGGER_ENABLED`) shows the ring buffer: Clear (hides what was logged before, by time; the messages stay in the buffer), a checkbox per level, an `ImGuiTextFilter`; a list logger's items nest under the message before them, the lines after the first of a multi-line message nest under it, and a system's consecutive messages nest under its first one until another logger logs; rows are flattened with the expanded state kept by message time, so `ImGuiListClipper` still draws only what's on screen. `ProfilerPanel` ("Profiler") lists each pass's GPU ms with a bar and their sum against the frame's time. `ViewportPanel` shows the renderer's scene target through an ImGui texture, asks it for the panel's size and rebuilds the texture when the image is recreated. `SystemsPanel` has the Reload button and a table of `GameAPILoader::GetSystems()` (`RegisteredSystem`: the descriptor, `Enabled` — kept by name in `m_DisabledSystems`, so it survives reloads — and `LastRunMs`).
- `Common.hpp` — platform, configuration and feature macros: `GRAM_CONFIG_DEBUG`/`_RELEASE`/`_FINAL` come from `GramEngine/CMakeLists.txt` as generator expressions (`$<$<CONFIG:Final>:GRAM_CONFIG_FINAL>`, `PUBLIC` on the three targets, so they reach the game and work in multi-config generators), Debug when none is defined; `GRAM_VULKAN_VALIDATION` / `GramValidationOnly(...)` only in Debug (the validation layers), `GRAM_IMGUI_ENABLED` (ImGui, the game's panels) everywhere but Final, `GRAM_EDITOR_ENABLED` / `GramEditorOnly(...)` (the engine's panels) only in Debug. On Windows, Final links without a console (`INTERFACE` link options on `GramEngine`: `/SUBSYSTEM:WINDOWS` + `/ENTRY:mainCRTStartup` with MSVC, so `main` stays the entry point; `-mwindows` with mingw). Apple/MoltenVK-only code is fenced with `GRAM_PLATFORM_APPLE`; capabilities such as `GRAM_GEOMETRY_SHADERS` are derived from the platform here, and renderer code tests the feature macro, not the platform.
- Shaders and textures: `GramShaders.cmake` provides `gram_add_hlsl_raster_shader(<target> <source>)` (entry points `VSMain`/`PSMain` → `<top-level build dir>/shaders/<name>.{vert,frag}.spv`) and `gram_add_hlsl_compute_shader` (`CSMain` → `<name>.compute.spv`), each recompiling when a `.hlsli` next to the shader changes (`gram_hlsl_headers`, a `CONFIGURE_DEPENDS` glob: dxc has no dependency output) and copying its output next to the target's executable after a build (`gram_copy_next_to`: a no-op under `gram build`, where the executable is in the build dir; how an IDE project's executable gets them), compiling a `.hlsl` file (a path relative to the caller's `CMakeLists.txt`) with the Vulkan SDK's `dxc`; `GramTextures.cmake` provides `gram_add_texture(<target> <source>)`, copying an image as-is into `<top-level build dir>/textures/`. Both belong to the game (`Game/Content/shaders/`, `Game/Content/textures/`); the engine only owns the tooling.
- Dependencies (root `Gram.ron`): vcpkg `vulkan` (headers only off Windows — the loader comes from the system/Vulkan SDK), `glfw3`, `glm`, `imgui` (features `glfw-binding`, `vulkan-binding`, `docking-experimental`), `stb` (only `stb_image`, compiled in `VulkanImage.cpp`, included `PRIVATE` to `GramRenderer`), spdlog via FetchContent.

`Game/Runtime/src/main.cpp`: `RuntimeApplication : GLFWApplication` registers a `World` and a `GameAPILoader` (from `GramEngine`) for `GameLogic`, creates one entity with a `Greeting` component (data in the `World`), then creates the `Gram::Editor` (after them: the panels keep references) and selects that entity in the inspector. Its own `GameUI` panel (added through `Editor::AddPanel`) only has the Greet button, emitting `"greet"` targeting that entity. `Greeting` is described once in `Game/Content/scripts/greeting.ron`; its C++ struct + descriptor live in `Game/Content/Components.generated.hpp` (the runtime adds `Content/` to its include path) (header-only, `inline` descriptors) and its Rust struct + `impl Component` in `Game/Content/components.generated.rs` (`#[path]` module `components`). `Content/lib.rs` is plumbing only: the `components` and `scripts` modules and the game's private `prelude` (`gram_core::prelude` + the components, so a script starts with `use crate::prelude::*;`); `scripts/mod.rs` is the game's manifest: the script modules and `export_game!` (`tick`, the `greet` events, and `bob`, which moves every small sphere up and down while playing). Both are generated by `gram build` (not checked in: plain `cargo` on a fresh clone needs one `gram generate` first); a new field shows up in the inspector without C++ changes, as long as its `FieldDescriptor::FieldType` has a case there. Its `RegisterPasses` adds the game's render pass: `RayTracePass` (`Game/Runtime/src/`, a compute dispatch from `Content/shaders/RayTracer.hlsl` into its own `rgba32f` output at twice the scene's size; a thin-lens camera (FOV, f-stop, focus distance, bokeh scale) edited in its `Debug/Ray Tracer` panel; the spheres are entities of the `World` with a `Sphere` (`center`, `radius`, `inner_radius`: hollow when > 0) and a `Material` (`albedo`, `fuzz`, `refract_index`, `absorption_distance`, `kind`: 0 Lambertian, 1 Metal, 2 Dielectric) component (`Content/scripts/sphere.ron`, `material.ron`), edited in the Outliner/Inspector; `PackScene` turns them into the GPU's `SphereData`/`MaterialData` every frame (sphere i's material is element i) and, when the packed bytes changed, rebuilds the BVH (`BVHTree.*`: spheres with a radius over 10, the ground, first and outside the tree (`LargeCount`), the rest reordered into leaves of at most 2, split by SAH (8 bins per axis, or no split when a leaf is cheaper) or at the middle of the longest axis, chosen in the panel's Build combo; `Validate` checks it and its stats show in the panel) and resets the accumulation; the shader walks the tree with a stack, nearer child first, when Use BVH is on (the default), and Show cost draws the primary ray's tests as a heat map; a Quality header sets SSAA (1x by default, 2x, 4x), samples per frame and max bounces), plus an `r32f` depth output (the first hit of a pinhole ray through each pixel's center, along the camera's axis) and a button generating the book's final scene; then three `PostProcessPass<Params>` (`PostProcessPass.hpp`: a fullscreen quad, a shader, a list of inputs (set 1, binding i = input i, as many as the generated `Params::InputCount`; set 0 = the uniform) and a `Fill` callback for its uniform; owns its output, following the first input's size, unless given one): `Accumulate` (a running average through the pipeline's blending, alpha = 1/(n+1), reset when the scene changes), `DepthOfField` (color + depth: a circle-of-confusion gather from the same lens settings; a pass-through unless the panel switches depth of field from the lens to the post-process) and `SSAA` (resolves the 2× image into the scene target); render targets are `std::shared_ptr`s passed between passes; every shader has a `.pass.ron`, so the uniform structs (`RayTracerParams`, `AccumulateParams`, `DepthOfFieldParams`, `SSAAParams`, `DefaultParams`: `TrianglePass`'s model/view/proj, its texture now in set 1), `SphereData`/`MaterialData`, the binding numbers, the shaders' declarations and their CMake lines are all generated (`Game/Runtime/CMakeLists.txt` includes `Content/Shaders.generated.cmake` and calls `gram_add_content_shaders(Runtime)`; the shader names come from `<Name>Params::Shader`); `TrianglePass` (the textured, rotating quad from `Default.hlsl`) stays in the tree, commented out there, as the graphics-pipeline example. Without ImGui (Final), `RegisterPasses` calls `RayTracePass::GenerateBookScene()` at startup (outside the ImGui fence: scene data, not UI), since the editor's button is the only other way to fill the scene. `CreateApplication` only fills the application spec.

Systems (steps 1–2 of `docs/wave-1-systems-design.md`, done 2026-11-02): the game's systems are plain Rust functions listed in `Game/Content/scripts/mod.rs` through `gram_core::export_game! { events: {…}, update: […] }`, which builds the `system::Entry` list (stage, name, event, and `run: fn(&Context)` — a non-capturing closure `|ctx| IntoSystem::run(&system, ctx)`, so C++ always calls the same signature). `on_load` calls `system::register(SYSTEMS)`, which sends one `Descriptor` per entry (index = position in the list) through `HostAPI::RegisterSystem`; C++ keeps copies in its registry, cleared before every unload. Each frame `GameAPILoader::OnDrawFrame` fills a `System::Context`, runs every `Update` system through `GameAPI::RunSystem(index, ctx)` (Rust's single dispatcher, inside `guard`), then hands each queued event to the systems registered for it; the queue is emptied every frame, loaded library or not. Adding a system is one name in `export_game!`: no C++ change, no version bump, picked up by a reload. A system declares what it needs in its signature (`fn greet(target: EventTarget, greetings: Query<Greeting>)`, done 2026-11-04): every parameter is a `SystemParam` (`type Item<'a>` + `fetch(&'a Context)`), and `IntoSystem<Marker>` is implemented by a `macro_rules!` for functions of 1 to 12 of them (`F: Fn(P…) + for<'a> Fn(P::Item<'a>…)`: the first bound infers the parameters, the higher-ranked one makes the call valid for the frame's `Context`; the marker tuple keeps the arities from overlapping). `&Context` is itself a parameter, so `fn(&Context)` systems still work. `EventTarget(Option<ObjectID>)`, `Time(f64)` and `DeltaTime(f32)` are generated by the crate-private `system_param!` (struct + `SystemParam` + `Deref`); C++ passes `InvalidObjectID` as the target of `Update` systems. `Query<T>` (a view over the `Context`; `trait Component: 'static`, components holding no references, so a `Ref<'a, T>` exists for any `'a`) has `get(id)` → `Option<Ref<'a, T>>` and `get_mut(id)` → `Option<RefMut<'a, T>>`, and `iter()`/`iter_mut()` → `(ObjectID, Ref/RefMut)` for every `T` (lazy: one guard per element, alive as long as the loop's variable; through `HostAPI::GetComponentCount`/`GetComponentAt`, the count read once), guards that hold the reference plus a `BorrowGuard` (like `RefCell`'s), tied to the `Context`'s lifetime so they can't outlive the system; `HostAPI::GetComponent(entity, T::ID)` gives the address, `None` for a dead entity or a missing component. `ctx.with::<T>(id, |c| …)` / `with_mut` (step 3) still exist underneath. Overlapping borrows are caught like a `RefCell` (step 5): `gram_core::scripting::borrow::BorrowGuard` keeps the active borrows in a `thread_local!` list (two reads may overlap; a write conflicts with anything on the same entity + component), panics with the caller's location (`#[track_caller]`, the panic outside the list's closure), and releases in `Drop`, so a system that panics doesn't leave its borrow behind. Verified: text edited in the inspector survives reloads, and Rust reads and writes it.

Reload: every 0.5 s `GameAPILoader::OnDrawFrame` compares the original library's write time with the last loaded one; on change `Reload()` runs `OnUnload`, unloads, copies under a new name (a new name each time, since macOS may not really unload a Rust dylib) and loads it again. A loader layer's `OnDrawFrame` always returns `true`: a failed reload means no Rust logic, not quitting. Panics never cross the boundary: each exported function's body runs inside `gram_core::interop::host::guard(f) -> Option<R>` (`catch_unwind`), and the panic hook `interop::host::init` installs logs `file:line:col: message` through the host instead of stderr. The contract types (`HostAPI`, `GameAPI`, `System::*`) are written twice by hand (C++, and Rust in `gram-core`: `interop::game`, `interop::host`, `scripting::system::context`), checked with size asserts on both sides; field order is the binary contract.

## Non-goals (current)

- No multiplayer/networking, no visual editor, no emulators/plugins — noted ideas, not now.
- No performance/optimization focus — functional correctness first.
- **Cross-compilation is scoped to `--ci` builds only** (added 2026-09-09): a `gram build --ci` iterates every target in `ModuleConfig.targets` (`linux`/`windows`/`macos`, skipping what the host can't build: `windows` cross-compiles via mingw from anywhere, `linux` ↔ `macos` doesn't); a plain `gram build` only compiles for the host it's run on, and `--target` builds a single target. Wave 1's native deps (Vulkan, GLFW, ImGui) cross-compile to Windows through vcpkg's `x64-mingw-static` triplet. In practice: develop on macOS, `gram build --ci` there, run the `.exe` natively on Windows and build Linux in WSL2.
- **No CI/CD until an explicit "Personal Builds" stage.** Planned design when that starts: GitHub Actions (free hosted runners) run classic Rust CI (`cargo build`/`test`/`clippy`) on every push; only on success, one step uses `tailscale/github-action` (ephemeral, ACL-scoped tailnet node, no exposure) to reach the private network and either mirror to Gitea (triggers the existing Jenkins webhook) or call Jenkins directly. A permanent self-hosted GitHub Actions runner was considered and rejected — it works (outbound-poll only, no port to open) but needs an ongoing-maintained process; the hosted-runner + ephemeral-Tailscale-hop design needs nothing running when idle.

## Repo model

Private GitHub repo (`Petrickah/gram-engine`) is the sole origin for now — deliberately not the Gitea-first convention used elsewhere in the author's `Projects` monorepo, chosen for durable code history and eventual Patreon early-access (repo-level separation when that happens, not a branch split). Gitea gets added later only as an automatic pull-mirror of GitHub, once "Personal Builds" actually starts — not before.
